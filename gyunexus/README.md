# GyuNexus

사용자 맥락을 이해하는 개인 AI 비서의 Core입니다. **GYUVIS**는 자연스러운 대화·개인 기억·선제 제안을 맡고, GyuNexus는 기억·도구·에이전트·자동화를 연결해 근거 중심의 자율 멀티에이전트 토론을 수행합니다.

> 현재는 MVP와 품질 검증 단계입니다. 파이프라인과 주요 안전 규칙은 구현·검증했지만, 자율 협업이 항상 높은 품질의 판단을 낸다고 보장하지는 않습니다.

- **GYUVIS** — 대화 맥락과 장기기억을 가진 개인 비서. 사용자의 상황을 바탕으로 기억·날씨·천문 정보 등을 근거로 먼저 제안합니다.
- **Multi-Agent Workspace** — Research / Idea / Developer / Critic 에이전트가 주제를 발굴·토론하고, 근거와 결과를 구조화해 저장합니다. 채택된 결과만 GYUVIS가 전달합니다.

## 목표

단순한 명령 실행 챗봇이 아니라, 사용자의 상황과 기록을 연결해 필요한 순간에 먼저 제안하는 개인 AI 비서를 지향합니다.

`Observe → Decide → Ask → Act → Report → Memory`

위험하거나 중요한 행동은 사용자의 승인을 전제로 하며, 단순하고 명확한 판단은 규칙으로 처리하고 요약·추론·의미 중복 판정처럼 필요한 지점에만 LLM을 사용합니다.

## 구조

```
backend/gyunexus/
  conversation.py   Conversation Engine   대화·세션, 대화 후 기억 학습
  memory.py         Memory Manager        기억 추출·중복 병합·검색
  context.py        Context Manager       접속(presence)·시간대·요일
  proactive.py      Proactive Engine      먼저 말 걸기 / 토론 결과 전달
  agents/           Agent Orchestrator    definitions.py(4 에이전트), orchestrator.py(토론)
  tools.py          Tool Registry         moon_phase, weather, wiki.search, notes.write
  policy.py         Policy & Approval     read 도구만 자동, 나머지는 사용자 승인
  scheduler.py      정기 자율 토론 + 능동 제안 루프
  llm.py            LLMProvider(교체 가능) + Gateway(사용량·예산)
frontend/           GyuNexus Dashboard (React + TS)
```

실시간 통신은 **SSE**(`GET /api/events`)입니다. 서버→클라이언트 단방향 이벤트(토론 발언, 에이전트 상태, 로그)만 필요하고 입력은 일반 POST로 충분하며, 브라우저가 재연결을 자동 처리하기 때문입니다.

## 실행 (Windows / PowerShell)

필요: Python 3.11+, Node 20+.

```powershell
copy .env.example .env      # OPENAI_API_KEY 입력

cd backend
D:\python\venv\Scripts\pip install -e ".[dev]"     # 공용 venv 사용 (새로 만들려면 python -m venv .venv)
D:\python\venv\Scripts\python -m uvicorn gyunexus.main:create_app --factory --port 8000
```

다른 터미널에서 개발용 대시보드:

```powershell
cd frontend
npm install
npm run dev          # http://localhost:5173  (/api 는 8000으로 프록시)
```

단일 서버로 쓰려면 `npm run build` 후 백엔드만 실행하면 `http://127.0.0.1:8000`에서 대시보드까지 제공됩니다.

## 테스트

```powershell
cd backend; D:\python\venv\Scripts\python -m pytest      # LLM은 테스트용 가짜 Provider로 대체
cd frontend; npm run typecheck
```

## 대화 문맥과 도구 라우팅 (`routing.py`, `conversation.py`)

대화 세션마다 현재 주제와 조건(날짜·시간대·장소)을 DB(`conversation_states`)에 저장하므로 서버를 재시작해도 이어집니다(6시간 이상 지나면 만료).

- "그럼 내일은?"은 날짜만, "강원도에서 보면?"은 장소만 바꾸고 나머지는 유지합니다. "그건 됐고 오늘 뉴스"처럼 주제가 바뀌면 조건을 초기화합니다(날씨↔은하수처럼 연관 주제만 날짜·장소를 이어받음).
- 규칙으로 확정되면 LLM 호출은 채팅 1회뿐입니다. 규칙으로 판단이 안 되는 후속 발화("그럼 거기는?")에만 짧은 의도 해석 호출이 1회 추가됩니다.
- 조건이 바뀌면 예보를 항상 다시 조회합니다. 조회에 실패하면(타임아웃 8초, 최대 3회 시도, 0.5초/1.5초 백오프) 실패 사실을 안내하고 이전 값은 현재 사실로 쓰지 않습니다. 지난 시간대·예보 범위 밖 날짜·모호한 장소는 값을 만들지 않고 되묻습니다.
- 응답 메시지의 `meta.trace`와 대화 화면의 "처리 과정"에서 해석된 의도, 이전 상태, 변경된 조건, 최종 조건, 선택된 도구와 이유, 결과, 부족한 정보를 볼 수 있습니다. 로그에서 API 키 패턴은 마스킹하고 위치 좌표는 남기지 않습니다.

## 토론 품질 규칙 (`agents/evidence.py`, `planner.py`, `ledger.py`, `orchestrator.py`)

LLM이 쓴 결과를 코드가 증거 기준으로 한 번 더 검증합니다(모두 규칙 기반, 추가 LLM 호출 없음).

- **증거와 경고**: 도구 결과에서 강수확률·구름량·달 밝기·조회 실패 같은 경고(`flags`)를 코드가 계산해 모든 에이전트와 종합 단계, 최종 결과(`warnings`)까지 전달합니다. 도구 실패도 '확인 불가' 증거로 남습니다.
- **주장 분류**: fact / interpretation(해석) / assumption(추정) / proposal(제안). `verified`는 인용한 증거에 실제로 있는 수치만 말하는 사실에만 붙고, "적합하다" 같은 판단이 섞이면 해석으로 분류됩니다.
- **충돌 차단**: 같은 날짜에 대해 증거 경고와 모순되는 서술("비 올 확률이 낮다" vs 강수 61%)은 확정하지 않고 `needs_research`로 내립니다. 존재가 확인되지 않은 장소·제품·기술 이름이 핵심인 아이디어도 채택하지 않습니다.
- **참가자 선택**: 규칙이 정합니다. 사실·수치·최신 정보가 필요한 제목이면 Research 필수, 소프트웨어 주제면 Developer, Critic은 항상 참여하며 선택/제외 이유가 `debate.plan`(DB·활동 로그)에 남습니다.
- **Critic**: 오류, 누락 조건, 증거 모순, 반례, 실행 위험 중 하나를 대상 인용·대안과 함께 제시해야 합니다. 상투적·중복·근거 없는 반박은 거부하고 토론당 최대 2회(발언당 1회) 다시 쓰게 합니다.
- **종료**: 합의(열린 반박·증거 충돌 없음), 추가 조사 필요, 정체(새 증거·새 반박·반박 처리가 없는 라운드), 최대 라운드, 토큰/일일 예산을 구분해 `stop_reason`과 `progress`에 남깁니다. 모두 동의해도 사실 확인이 필요한 주제에 검증된 사실이 없으면 합의로 보지 않습니다.
- **아이디어 상태**: `accepted`(검토 완료) / `needs_research`(근거 필요) / `discarded`(폐기, 감사용 기록만 유지). 활성 아이디어 목록(`GET /api/ideas`)과 GYUVIS 추천·전달에는 폐기된 것과 검증되지 않은 것을 쓰지 않으며, 중요도가 높아도 `accepted`가 없으면 전달하지 않습니다.
- **주제 발굴**: 가장 적게 다룬 기억을 중심으로 삼게 하고, 문자 유사도로 못 잡는 같은 뜻의 주제는 비슷한 기존 주제가 있을 때만 짧은 LLM 판정(약 $0.0001) 1회로 거릅니다.

## 자율 토론 규칙 (코드 위치: `agents/orchestrator.py`, `scheduler.py`)

| 항목 | 동작 |
|---|---|
| 주제 | 큐(수동·이벤트)에 있으면 우선, 없으면 사용자 기억·최근 주제로 LLM이 발굴. 새 관심사를 기억하면 이벤트 주제가 자동 생성됩니다 |
| 일정 | `DEBATE_INTERVAL_MINUTES`마다 1건. 대시보드에서 ON/OFF·즉시 실행 가능 |
| 중복 방지 | 기존 주제와 문자 bigram 유사도 ≥ 0.6이면 거절(발굴은 최대 3회 재시도) |
| 참여자 | 규칙으로 선택합니다. 사실·수치·최신 정보가 필요하면 Research, 소프트웨어 주제면 Developer를 포함하며 Critic은 항상 참여합니다. 선택·제외 사유를 기록합니다 |
| 종료 | 합의, 추가 조사 필요, 정체, 최대 라운드, 토론당 토큰 상한, 일일 자율 예산, LLM 오류를 구분해 기록합니다 |
| 비용 | 모든 호출을 `llm_usage`에 기록. 자율 작업은 `DAILY_BUDGET_USD` 초과 시 중단 |
| 사실 구분 | 주장은 fact / interpretation / assumption / proposal으로 분류합니다. **도구 증거 id를 인용하고 그 증거에 실제 있는 수치·사실만 verified**가 됩니다 |
| 결과 | 요약·결정·아이디어·주장·열린 질문·중요도·경고를 DB에 저장합니다. `accepted`인 아이디어만 GYUVIS 전달 후보가 되며, 증거 경고와 충돌하면 전달하지 않습니다 |
| 위험 작업 | 에이전트는 읽기 도구만 직접 호출. 파일 변경 등은 `proposed_actions` → **승인 탭**에서 사용자가 승인해야 실행 |

## 현재 상태와 검증

**구현됨**: FastAPI 서버, React 대시보드, OpenAI 연동, 텍스트 대화·기록 저장, 기억 자동 추출/저장/활용, 4 에이전트 등록, 자율 토론(주제 발굴·참여자 선택·반박·종합), 토론/아이디어/증거 저장, 정기 실행, 에이전트 상태·실행 로그, 승인 큐, 접속 감지 기반 능동 제안(달 위상+날씨), 토론 결과 전달, SQLite(`GYUNEXUS_DATABASE_URL`로 MariaDB 전환 가능).

- 백엔드 테스트 **86개 통과**(기존 47개, 신규 39개) 및 프런트엔드 빌드를 확인했습니다.
- 실제 OpenAI **gpt-4o-mini**와 임시 DB로도 검증했습니다. 사용자 실제 DB에는 쓰지 않았습니다.
- 실제 재실행에서 Research 누락, 형식적 반박, 증거 경고 누락은 재현되지 않았습니다.
- 테스트에는 Research 필수/생략, 증거와 충돌하는 결론 거부, 근거 없는 고유명사, 내용 없는 Critic 반박, 타당한 주장 보존, 반복 반박 정체 종료, 폐기 아이디어 추천 차단, 도구 오류·경고 전달, 토큰·예산 상한이 포함됩니다.
- 이번 범위에서 새 UI·음성·HUD·PC 제어는 추가하지 않았습니다. 화면에는 채택·추가 조사 필요·폐기 상태 라벨만 반영했습니다.

## 알려진 제약과 이후 평가

- 실제 LLM에서 합의 종료와 정체 종료는 아직 충분히 반복 검증하지 못했습니다. 실제 실행은 최대 라운드 종료가 많았습니다.
- Critic은 증거 모순을 지적할 수 있지만, 날짜·문맥의 의미까지 정확히 판별하는 것은 보장하지 못합니다.
- 아이디어 중요도 보정은 미완성이어서 채택된 제안이 사소할 수 있습니다.
- 계절·요일·준비물 같은 일반 지식은 증거 부족으로 `needs_research`에 남기 쉽고, 기술명 존재 확인 규칙에는 오탐 가능성이 있습니다.
- 장소 추천에는 신뢰도 높은 장소 데이터 도구가 부족합니다. 한국어 문장 패턴에 의존하는 충돌·고유명사·반복 판정에도 오탐과 미탐이 있을 수 있습니다.
- Research의 관련 도구 조회가 다음 라운드까지 늦어질 수 있으며, 이벤트 기반 자율 시작·장시간 운영·일일 예산 소진·승인 큐 실제 사용은 더 검증해야 합니다.
- 기억 검색은 임베딩 없이 문자 유사도·중요도·최신성으로 순위화합니다. 기억이 수백 건을 넘으면 임베딩 도입을 검토해야 합니다.
- 대화 맥락은 최근 20개 메시지 창이며 오래된 대화 요약과 응답 토큰 스트리밍은 없습니다. 일반 웹 검색·뉴스 조회, 월출·월몰 계산, 인증, 정식 DB 마이그레이션 도구도 아직 없습니다.

다음 단계는 기능을 늘리기보다 여러 주제와 시드에서 Research 선택, Critic 품질, 증거-결론 일관성, 제안의 유용성과 중요도를 반복 평가하는 것입니다.
