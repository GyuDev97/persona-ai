# GyuNexus

사용자 맥락을 이해하는 개인 AI 비서의 Core입니다. **GYUVIS**는 자연스러운 대화·개인 기억·선제 제안을 맡고, GyuNexus는 기억·도구·에이전트·자동화를 연결해 근거 중심의 자율 멀티에이전트 토론을 수행합니다.

> 현재는 MVP와 품질 검증 단계입니다. 파이프라인과 주요 안전 규칙은 구현·검증했지만, 자율 협업이 항상 높은 품질의 판단을 낸다고 보장하지는 않습니다.

- **GYUVIS** — 대화 맥락과 장기기억을 가진 개인 비서. 사용자의 상황을 바탕으로 기억·날씨·천문 정보 등을 근거로 먼저 제안합니다.
- **Multi-Agent Workspace** — Research / Idea / Developer / Critic 에이전트가 주제를 발굴·토론하고, 근거와 결과를 구조화해 저장합니다. 채택된 결과만 GYUVIS가 전달합니다.

## 목표

단순한 명령 실행 챗봇이 아니라, 사용자의 상황과 기록을 연결해 필요한 순간에 먼저 제안하는 개인 AI 비서를 지향합니다.

`Observe → Decide → Ask → Act → Report → Memory`

위험하거나 중요한 행동은 사용자의 승인을 전제로 하며, 단순하고 명확한 판단은 규칙으로 처리하고 요약·추론·의미 중복 판정처럼 필요한 지점에만 LLM을 사용합니다.

## 구조

```
backend/gyunexus/
  conversation.py   Conversation Engine   대화·세션, 대화 후 기억 학습
  memory.py         Memory Manager        기억 추출·중복 병합·검색
  context.py        Context Manager       접속(presence)·시간대·요일
  proactive.py      Proactive Engine      먼저 말 걸기 / 토론 결과 전달
  agents/           Agent Orchestrator    definitions.py(4 에이전트), orchestrator.py(토론)
  tools.py          Tool Registry         moon_phase, weather, wiki.search, notes.write
  policy.py         Policy & Approval     read 도구만 자동, 나머지는 사용자 승인
  scheduler.py      정기 자율 토론 + 능동 제안 루프
  llm.py            LLMProvider(교체 가능) + Gateway(사용량·예산)
frontend/           GyuNexus Dashboard (React + TS)
```

실시간 통신은 **SSE**(`GET /api/events`)입니다. 서버→클라이언트 단방향 이벤트(토론 발언, 에이전트 상태, 로그)만 필요하고 입력은 일반 POST로 충분하며, 브라우저가 재연결을 자동 처리하기 때문입니다.

## 실행 (Windows / PowerShell)

필요: Python 3.11+, Node 20+.

```powershell
copy .env.example .env      # OPENAI_API_KEY 입력

cd backend
D:\python\venv\Scripts\pip install -e ".[dev]"     # 공용 venv 사용 (새로 만들려면 python -m venv .venv)
D:\python\venv\Scripts\python -m uvicorn gyunexus.main:create_app --factory --port 8000
```

다른 터미널에서 개발용 대시보드:

```powershell
cd frontend
npm install
npm run dev          # http://localhost:5173  (/api 는 8000으로 프록시)
```

단일 서버로 쓰려면 `npm run build` 후 백엔드만 실행하면 `http://127.0.0.1:8000`에서 대시보드까지 제공됩니다.

## 대화 문맥과 도구 라우팅 (`routing.py`, `conversation.py`)

대화 세션마다 현재 주제와 조건(날짜·시간대·장소)을 DB(`conversation_states`)에 저장하므로 서버를 재시작해도 이어집니다(6시간 이상 지나면 만료).

- "그럼 내일은?"은 날짜만, "강원도에서 보면?"은 장소만 바꾸고 나머지는 유지합니다. "그건 됐고 오늘 뉴스"처럼 주제가 바뀌면 조건을 초기화합니다(날씨↔은하수처럼 연관 주제만 날짜·장소를 이어받음).
- 규칙으로 확정되면 LLM 호출은 채팅 1회뿐입니다. 규칙으로 판단이 안 되는 후속 발화("그럼 거기는?")에만 짧은 의도 해석 호출이 1회 추가됩니다.
- 조건이 바뀌면 예보를 항상 다시 조회합니다. 조회에 실패하면(타임아웃 8초, 최대 3회 시도, 0.5초/1.5초 백오프) 실패 사실을 안내하고 이전 값은 현재 사실로 쓰지 않습니다. 지난 시간대·예보 범위 밖 날짜·모호한 장소는 값을 만들지 않고 되묻습니다.
- 응답 메시지의 `meta.trace`와 대화 화면의 "처리 과정"에서 해석된 의도, 이전 상태, 변경된 조건, 최종 조건, 선택된 도구와 이유, 결과, 부족한 정보를 볼 수 있습니다. 로그에서 API 키 패턴은 마스킹하고 위치 좌표는 남기지 않습니다.

## 능동 제안 (`proactive.py`, `suggestions.py`)

GYUVIS는 "필요할 때만 먼저 말한다"를 규칙으로 구현합니다. 모든 후보는 `suggestions` 테이블에 점수·이유와 함께 남고(전달하지 않은 후보 포함), 대시보드의 **능동 제안** 탭에서 볼 수 있습니다.

1. **이벤트**: 대시보드 접속(30분 이상 비었다 돌아옴), 정시 점검, 채택된 아이디어 생성, 사용자가 요청한 재알림 시점. 같은 이벤트의 짧은 반복은 무시합니다(재시작 후에도 유지).
2. **관측 vs 추정**: 접속·시각·요일은 관측, "퇴근했을 것"은 낮은 확신의 추정으로 분리해 기록하고, 문장에서 단정하지 않습니다.
3. **후보 생성**: 기억(은하수·출사 등)이 있고 날씨·달 위상 도구 결과가 있을 때만 출사 후보를 만듭니다(금·목요일에는 주말 밤 포함). 기억이 없거나 조회가 실패하면 후보를 만들지 않거나 폐기하고 추측하지 않습니다. `accepted` 아이디어만 아이디어 후보가 됩니다(경고는 그대로 전달, `discarded`·`needs_research`는 후보 제외).
4. **게이트(하드 규칙)**: 설정 꺼짐·주제 꺼짐·만료·거절/연기 직후·3회 이상 거절·중복·조용한 시간(보류)·하루 한도(보류)·쿨다운(보류).
5. **점수**: 관련성 .30 + 유용성 .25 + 시간 민감도 .15 + 근거 .20 + 방해 가능성 .10, 거절 이력 감점·관심 이력 가점. 관측 조건 점수가 0.65 미만이면 다른 점수가 높아도 출사를 권하지 않습니다. 0.62 이상 전달 후보, 0.40 미만 폐기, 사이는 LLM이 판단. 버려지는 후보에는 LLM 호출이 없고, 전달 후보도 1회뿐입니다.
6. **사용자 반응**(제안 직후 첫 답과, 관심을 보인 뒤의 거절·재알림·중지): 관심/자세히/거절/나중에/알림 중지/일반 대화. 거절은 그날(또는 말한 날짜까지) 같은 주제를 막되 장기기억에는 저장하지 않고, "그만 알려줘"만 지속적 선호도(설정 + 기억)로 저장합니다. "다음 주 금요일에 다시 알려줘"는 실제 날짜 재알림으로 등록(중복 병합)되고 시점이 오면 **새로 조회한 데이터로 다시 판단**합니다(조건이 나쁘면 사실대로 알림, 조회 실패는 30분 간격 3회 재시도 후 실패를 알림).
7. **대화 연결**: 제안한 주제·날짜·시간대를 대화 상태로 저장하고 근거를 다음 응답 프롬프트에 넣어, "어디가 좋은데?", "토요일 새벽은?"이 같은 문맥에서 처리됩니다.
8. **사용자 통제**(`GET/PUT /api/proactive/settings`): 켜기/끄기, 하루 최대 횟수, 조용한 시간대(기본 23:00-07:00), 주제별 허용.

## AI 직원 (`workers.py`, `workers_api.py`, `workspace.py`)

**직원 탭**(에이전트 탭 오른쪽)에서 직원을 등록하고 업무를 배정합니다. 직원은 상시 실행되는 LLM이 아니라 업무가 실행될 때만 기존 LLM Provider를 호출하는 책임 단위입니다. 직원 등록만으로는 아무것도 실행되지 않고, 업무는 직접 "지금 실행"하거나 정기 실행으로 설정해야 합니다.

- **실행 라이프사이클**: `pending → running → reviewing → awaiting_approval → completed`, 예외는 `failed`(원인 `error_kind`) / `cancelled` / `rejected`(승인 반려) / `needs_input`(자료 부족). 업무 1건당 진행 중 실행은 1개(승인 대기 포함), 정기 슬롯은 한 번만 실행(DB 유니크 키), 재시작 시 중단된 실행은 자동 재실행 없이 `interrupted`로 표시합니다.
- **기본 방식**: 단일 LLM + 증거 번들(제공 자료·도구 결과) + 코드 검증. 도구 호출 계획 1회(도구가 있을 때) + 작성 1회 + 기준 검수 1회가 기본이고, 검증 실패 시 사유를 주고 1회만 다시 씁니다. 멀티 에이전트 토론은 시작하지 않으며, 업무에서 허용하면 이미 끝난 토론의 채택 결과만 증거로 가져옵니다.
- **검증**(LLM의 "다 했다"는 말은 근거가 아님): 길이·형식·필수 섹션/키, 인용한 근거 번호의 실재, 주장별 인용, 본문 수치가 근거에 있는지 코드가 검사하고, 자연어 완료 기준은 검수 호출이 **본문에서 그대로 복사한 문장**으로 증명해야 통과합니다. 검증을 통과하지 못한 결과물은 `-unverified` 파일로 보관만 하고 승인 요청도 만들지 않습니다.
- **권한**: 업무 도구는 직원 허용 도구의 부분집합이며 LLM이 무엇을 요청해도 허용 목록 밖은 실행하지 않습니다. 쓰기/외부 도구는 "승인 후 쓰기" 직원만 쓸 수 있고, 그때도 기존 Policy 승인 큐를 거칩니다. 결과물 확정도 승인 항목(`worker.finalize`)이며 승인 시점에 파일 sha256이 요청 때와 같은지 다시 확인합니다. 자료 속 지시문은 데이터로만 취급합니다.
- **예산**: 업무·직원 최대 비용 중 작은 값이 실행 상한이며, LLM 호출 전에 예상 최대 비용이 남은 한도를 넘으면 호출하지 않습니다. 정기 실행은 기존 일일 자율 예산도 적용됩니다.
- **작업 공간**: `data/workspace/w{직원}/inputs|runs/r{실행}/`. 파일명은 서버가 정하고(LLM 지정 불가), 경로 구분자·`..`·예약 이름·허용 밖 확장자·작업 공간 밖 경로를 거부하며 덮어쓰지 않습니다.
- **GYUVIS 연동**: 승인 필요·완료·실패·자료 부족 시 한 번만 알립니다(능동 제안의 `worker` 주제: 조용한 시간 보류, 설정 끄기 존중, 같은 결과 중복 방지, 같은 실패는 하루 1회, 같은 업무 완료 알림은 60분 간격). 알림 뒤 "어떤 내용인데?"에는 실제 결과물 본문을 조회해 설명하고, 승인은 채팅이 아니라 승인 탭/직원 탭에서만 가능합니다.
- 샘플 템플릿 "콘텐츠 담당"(개발 기록 → 기술 블로그 초안, 자료가 없으면 자료를 요청)은 폼을 채워 줄 뿐 자동 등록·실행되지 않습니다. API: `/api/workers`(+`/options`, `/{id}/tasks`, `/tasks/{id}/run`, `/runs`, `/runs/{id}`, `/{id}/inputs`).

## 워크플로: 여러 AI 직원의 협업 (`workflows.py`, `workflows_api.py`)

자연어 목표 하나를 여러 직원이 나눠 수행합니다(**워크플로** 화면). 실행 엔진은 새로 만들지 않고, 각 단계가 기존 Worker 업무(Task)를 `WorkerService.start()`로 실행한 것입니다. 오케스트레이터에는 직원·업무·도메인 이름이 하드코딩돼 있지 않습니다(테스트가 소스를 검사).

- **계획**: 플래너(LLM)가 DB 의 직원·업무 카탈로그(메타데이터만, 자료 본문 미전송)를 보고 DAG 를 제안하고, **서버가 검증**합니다: 스키마, 직원·업무 존재와 소유 관계, 비활성·일시정지 거부, 순환·자기 의존·없는 선행 단계, 단계 수(12), 자료가 필요한 업무의 입력 연결, 예산(단계 상한 합 ≤ 예산). 검증에 실패하면 오류를 알려 한 번만 다시 제안받고, 그래도 실패하면 단계 없는 계획과 사유만 저장해 실행할 수 없습니다. 계획은 사용자가 확인·수정한 뒤 실행하며(`auto_run`을 명시한 경우에만 즉시 실행), 시작 직전에 다시 검증합니다.
- **Artifact 연결**: 선행 단계의 결과물은 경로가 아닌 **Artifact ID + 버전 + sha256 고정 참조**로 후속 실행의 입력 자료가 됩니다. 승인까지 끝난(`completed`) 검증된 결과물만 참조할 수 있고, 읽을 때마다 저장된 해시와 파일의 해시를 다시 확인하며(변조 시 거부), 원본은 수정하지 않습니다. 여러 선행 결과물을 한 단계에 전달할 수 있고 `GET /api/artifacts/{id}/lineage`로 계보를 볼 수 있습니다.
- **실행**: 선행 단계가 모두 `completed`인 단계만 시작하고, 독립 단계는 병렬(기본 3개)로 실행합니다. 승인이 필요한 단계는 승인 전에 다음 단계로 진행하지 않으며, 기존 승인 화면에서 승인하면 자동으로 이어집니다. 도구 권한·승인·비용 한도는 각 Worker/Task 의 설정 그대로이며 워크플로 지시(`directive`)로 확대할 수 없습니다.
- **비용·중복 방지**: 워크플로 총예산(계획 생성 포함)을 시작 전·단계 시작 직전에 확인하고, 같은 업무는 동시에 하나만 실행합니다(워크플로 락 + 업무 단위 진행 중 실행 검사 + `slot_key` 유니크).
- **계획 생성 실패와 복구**: 계획 생성이 실패하면 워크플로는 단계 없이 `plan_state=failed`로 남고, 실패 사유는 실행 오류(`error`)가 아니라 `plan_error`(+`plan_error_kind`: `budget` 예산 때문에만 실패 / `invalid` 그 밖의 검증 실패, 실패 당시 예산 `plan_error_budget_usd`)에 둡니다. 플래너 제안 원본은 `proposed_steps`에 보관됩니다. 예산을 올리면(`PUT /api/workflows/{id}`) **예산 때문에만** 실패했고 제안이 남아 있을 때 새 LLM 호출 없이 제안을 현재 저장된 예산으로 다시 검증해 단계를 만들고 실패 상태를 해소합니다(예산 외 사유는 증액만으로 해소되지 않음). `POST /api/workflows/{id}/replan`은 같은 재검증을 수동으로 하고, 제안이 없거나(이전 버전 데이터)·예산 외 사유이거나·`{"regenerate": true}`이면 현재 예산으로 계획을 다시 생성해 비용을 `planning_cost_usd`에 누적합니다. 어느 경우든 워크플로 ID·예산 변경 이력·실행 이력은 그대로이고 복구 후에도 `planned` 상태로 사용자의 시작·승인을 기다립니다(자동 시작 없음). 과거 실패는 `workflow_plan_attempts`(상세의 `plan_attempts`)에 이력으로 남고 현재 오류로는 더 보이지 않습니다. 유효한 계획이 있는데 예산 때문에 시작만 막힌 경우는 계획 실패가 아니라 상세의 `start_check`로 따로 알립니다. 시작·계획 저장 전 검증은 항상 현재 저장된 예산을 씁니다. 이전 버전이 `error`/`plan_notes`에만 적어 둔 실패는 서버 시작 시 이 모델로 옮겨지며(단계·실행·비용·예산 이력은 건드리지 않는 멱등 보정) 이 경우 제안이 없어 `replan`이 새로 생성합니다.
- **누적 비용 집계**: 워크플로의 사용액은 `계획 생성 비용 + WorkerRun.workflow_id 가 이 워크플로인 모든 실행의 비용`(`_spent` 하나)이며 예산 검사·예산 변경 최소 금액·상세/목록 비용이 모두 이 값을 씁니다. 계획 수정으로 단계를 삭제·교체해도 줄지 않고, 실행된 적이 있는 단계는 행을 지우지 않고 `removed`로 보존합니다(실행 이력·Artifact 계보·비용 귀속 유지, step id 재사용 방지). 삭제된 단계 비용은 `removed_steps`로 따로 보이며 이중 집계되지 않습니다. 이전 데이터는 서버 시작 시 `slot_key`(`wf{워크플로}:…`)로 소속 워크플로를 복원합니다(비용·이력은 바꾸지 않는 멱등 보정).
- **총예산 변경**(워크플로 화면의 ‘예산 변경’, 계획 수정 화면의 예산 입력란, `PUT /api/workflows/{id}` `budget_usd`, `PUT .../plan`의 `budget_usd`): 생성 때와 같은 검증(숫자, 0 초과, 상한 이하, USD)에 더해 새 예산 ≥ **이미 사용한 비용(계획 생성 포함) + 남은 단계 상한**(대기 단계의 상한 + 실행 중 단계의 남은 상한)이어야 합니다. 실행 전·실행 중·승인 대기·일시정지·실패 상태에서 가능하고 완료·취소 상태는 차단합니다. 변경은 워크플로 락 안에서 처리되어 단계 시작과 충돌하지 않고, 증액하면 예산 부족으로 거부됐던 단계가 즉시 다시 실행됩니다. 변경 전후 값·당시 사용액·남은 요구량·상태·시각은 `workflow_budget_changes`에 남으며(`budget_history`), 실행 이력·승인·Artifact 참조·비용 기록은 바뀌지 않습니다. 프런트엔드는 `GET /api/workflows/options`의 상한을 받아 같은 규칙을 입력 단계에서 검사합니다.
- **제어**: 실행·일시정지(새 단계만 멈춤)·재개·취소(진행 중 실행 중단, 승인 항목 반려)·실패 단계만 재시도·계획 수정(실행 중이거나 끝난 단계는 변경 불가). 모든 상태·의존성·비용·모델·입력 참조·실패 원인이 DB 에 저장되어 재시작 후에도 이어지고, 중단된 단계는 `interrupted`로 표시되며 재개 시 해당 단계만 다시 시작합니다.

## 뉴스 수집·검증 도구 (`newstools.py`, `netguard.py`, `news_report.py`)

AI 직원이 쓸 수 있는 읽기 전용 도구 3개입니다. 직원 허용 도구와 업무 허용 도구를 **둘 다** 통과해야 실행되며, 기존 직원에게 자동으로 부여되지 않습니다.

- `rss.fetch`: 공식 기술 블로그·언론 RSS/Atom 24개(OpenAI, Google, Microsoft, NVIDIA, GitHub, Hugging Face, AWS, Meta, 카카오, 네이버 D2, 전자신문, ZDNet Korea, AI타임스, TechCrunch 등)를 수집합니다. 피드 URL 은 2026-10-18 에 실제 200 응답과 항목을 확인한 것만 등록했습니다(동작하지 않아 제외: Microsoft AI 블로그 410, Anthropic 404, IT조선·블로터 404, VentureBeat 429). 일부 피드가 실패해도 나머지는 계속하고, 전부 실패할 때만 오류(`source_unavailable`)입니다.
- `news.search`: 큐레이션된 피드 전체의 키워드 검색 + Hacker News Algolia API(공식·무료·키 불필요). Google News RSS 는 링크가 원문 조회 불가능한 래퍼 URL 이고, GDELT 는 요청 제한(429)이 심해 제외했습니다. 한국어 전용 검색 API(예: 네이버 검색 API)는 키 발급이 필요해 넣지 않았습니다.
- `web.fetch`: 원문 본문 발췌와 게시일·출처 메타데이터를 추출합니다. 원문은 저장하지 않고 발췌만 돌려줍니다.
- 날짜는 UTC 로 돌려주며 발행일(`published_at`)과 수집일(`collected_at`/`seen_at`)을 구분합니다. 시간대·시각이 없는 날짜는 가정 사실을 표시합니다. 같은 기사는 URL 정규화(추적 파라미터 제거)와 제목 유사도로 합칩니다.
- **SSRF 방지**: http/https 만, 사용자 정보·80/443 외 포트·로컬 이름 거부, DNS 결과가 모두 공인 IP 여야 함(사설·루프백·링크로컬·CGNAT·IPv4-mapped IPv6 거부), 리다이렉트는 매 단계 재검증(최대 4회), 타임아웃·크기 상한. 남은 한계: 검증과 연결 사이 DNS rebinding 은 연결 IP 를 고정하지 않아 완전히 막지 못합니다.
- **뉴스 조사 보고서**(업무 `report_kind=news`): 모델은 사실 문장·기술적 의미·블로그 제목 후보만 쓰고, URL·게시일·수집 시각·검증 상태는 코드가 도구 결과에서 기록해 Markdown 을 조립합니다. 검증 상태는 ‘원문 확인 / 공식 피드 기준(원문 미확인) / 검색·피드 결과만(미검증) / 원문 확인 실패(미검증)’이며 모델이 격상할 수 없습니다. 수집되지 않은 URL·기준 시간을 넘긴 기사·출처 텍스트로 뒷받침되지 않는 사실 문장(수치 포함)은 제외됩니다. `web.fetch` 는 수집 목록이나 업무 지시에 있는 URL 만 조회할 수 있어 원문 속 링크를 따라가지 않으며, 원문 속 지시문은 데이터로만 취급합니다.
- 템플릿 “IT·AI 뉴스 리서처”(직원 화면에서 폼을 채워 줌, 자동 등록·실행 없음): 2라운드 도구 계획(후보 수집 → 원문 확인), 호출 14건·$0.08·300초 상한, 결과물은 승인 대기. 블로그 게시 기능은 없습니다.

## 토론 품질 규칙 (`agents/evidence.py`, `planner.py`, `ledger.py`, `orchestrator.py`)

LLM이 쓴 결과를 코드가 증거 기준으로 한 번 더 검증합니다(모두 규칙 기반, 추가 LLM 호출 없음).

- **증거와 경고**: 도구 결과에서 강수확률·구름량·달 밝기·조회 실패 같은 경고(`flags`)를 코드가 계산해 모든 에이전트와 종합 단계, 최종 결과(`warnings`)까지 전달합니다. 도구 실패도 '확인 불가' 증거로 남습니다.
- **주장 분류**: fact / interpretation(해석) / assumption(추정) / proposal(제안). `verified`는 인용한 증거에 실제로 있는 수치만 말하는 사실에만 붙고, "적합하다" 같은 판단이 섞이면 해석으로 분류됩니다.
- **충돌 차단**: 같은 날짜에 대해 증거 경고와 모순되는 서술("비 올 확률이 낮다" vs 강수 61%)은 확정하지 않고 `needs_research`로 내립니다. 존재가 확인되지 않은 장소·제품·기술 이름이 핵심인 아이디어도 채택하지 않습니다.
- **참가자 선택**: 규칙이 정합니다. 사실·수치·최신 정보가 필요한 제목이면 Research 필수, 소프트웨어 주제면 Developer, Critic은 항상 참여하며 선택/제외 이유가 `debate.plan`(DB·활동 로그)에 남습니다.
- **Critic**: 오류, 누락 조건, 증거 모순, 반례, 실행 위험 중 하나를 대상 인용·대안과 함께 제시해야 합니다. 상투적·중복·근거 없는 반박은 거부하고 토론당 최대 2회(발언당 1회) 다시 쓰게 합니다.
- **종료**: 합의(열린 반박·증거 충돌 없음), 추가 조사 필요, 정체(새 증거·새 반박·반박 처리가 없는 라운드), 최대 라운드, 토큰/일일 예산을 구분해 `stop_reason`과 `progress`에 남깁니다. 모두 동의해도 사실 확인이 필요한 주제에 검증된 사실이 없으면 합의로 보지 않습니다.
- **아이디어 상태**: `accepted`(검토 완료) / `needs_research`(근거 필요) / `discarded`(폐기, 감사용 기록만 유지). 활성 아이디어 목록(`GET /api/ideas`)과 GYUVIS 추천·전달에는 폐기된 것과 검증되지 않은 것을 쓰지 않으며, 중요도가 높아도 `accepted`가 없으면 전달하지 않습니다.
- **주제 발굴**: 가장 적게 다룬 기억을 중심으로 삼게 하고, 문자 유사도로 못 잡는 같은 뜻의 주제는 비슷한 기존 주제가 있을 때만 짧은 LLM 판정(약 $0.0001) 1회로 거릅니다.

- 테스트에는 Research 필수/생략, 증거와 충돌하는 결론 거부, 근거 없는 고유명사, 내용 없는 Critic 반박, 타당한 주장 보존, 반복 반박 정체 종료, 폐기 아이디어 추천 차단, 도구 오류·경고 전달, 토큰·예산 상한이 포함됩니다.
- 이번 범위에서 새 UI·음성·HUD·PC 제어는 추가하지 않았습니다. 화면에는 채택·추가 조사 필요·폐기 상태 라벨만 반영했습니다.

## 알려진 제약과 이후 평가

- 실제 LLM에서 합의 종료와 정체 종료는 아직 충분히 반복 검증하지 못했습니다. 실제 실행은 최대 라운드 종료가 많았습니다.
- Critic은 증거 모순을 지적할 수 있지만, 날짜·문맥의 의미까지 정확히 판별하는 것은 보장하지 못합니다.
- 아이디어 중요도 보정은 미완성이어서 채택된 제안이 사소할 수 있습니다.
- 계절·요일·준비물 같은 일반 지식은 증거 부족으로 `needs_research`에 남기 쉽고, 기술명 존재 확인 규칙에는 오탐 가능성이 있습니다.
- 장소 추천에는 신뢰도 높은 장소 데이터 도구가 부족합니다. 한국어 문장 패턴에 의존하는 충돌·고유명사·반복 판정에도 오탐과 미탐이 있을 수 있습니다.
- Research의 관련 도구 조회가 다음 라운드까지 늦어질 수 있으며, 이벤트 기반 자율 시작·장시간 운영·일일 예산 소진·승인 큐 실제 사용은 더 검증해야 합니다.
- 기억 검색은 임베딩 없이 문자 유사도·중요도·최신성으로 순위화합니다. 기억이 수백 건을 넘으면 임베딩 도입을 검토해야 합니다.
- 대화 맥락은 최근 20개 메시지 창이며 오래된 대화 요약과 응답 토큰 스트리밍은 없습니다. 일반 웹 검색·뉴스 조회, 월출·월몰 계산, 인증, 정식 DB 마이그레이션 도구도 아직 없습니다.

다음 단계는 기능을 늘리기보다 여러 주제와 시드에서 Research 선택, Critic 품질, 증거-결론 일관성, 제안의 유용성과 중요도를 반복 평가하는 것입니다.
